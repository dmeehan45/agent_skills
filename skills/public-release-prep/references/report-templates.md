## 1. Phase 1 — publication-readiness audit

The deliverable of the audit phase. Ends with questions and a verdict, then
waits for approval.

```markdown
# Publication-readiness audit — <repo name>
Audited <date> · <commit SHA> · branch <branch>

## 1. What this project is
Plain language, 3-6 sentences, from reading the code rather than the README:
what it does, what it is built with, whether the implementation matches its
apparent purpose, and whether it is realistically a template, a reference
implementation, a demo, or an archival example. Say which and why.

## 2. Publication readiness

| # | Severity | Finding | Evidence | Risk if published as-is | Proposed treatment |
| --- | --- | --- | --- | --- | --- |
| 1 | Blocker | Live-format credential in history | `.env` at `8aaf3dc`, fingerprint `28be19ba` (value not shown) | Credential exposed to anyone cloning | Rotate at provider; fresh-history export |
| 2 | High | No LICENSE | repo root | Public but not legally reusable — defeats the template goal | Add after ownership confirmed (Q1) |
| 3 | Medium | Install fails on lockfile | `npm ci` → ERESOLVE (output below) | Nobody can run it | Repair (§5) |
| 4 | Low | 12 MB of screenshots in history | `inventory/largest-tracked-files.txt` | Slow clone; check for leaks | Review; exclude from snapshot |

## 3. Blockers
Anything that must be resolved before publication is possible at all —
ownership, confidentiality, licensing, live credentials, third-party rights.
State what is blocked, what would unblock it, and who must act. If there are
none, say so explicitly.

## 4. Questions
Only what the repo cannot answer. Numbered, so answers can be given inline.
Ownership and the never-publish list are always asked. Where there is a
sensible default, name it.

## 5. Proposed cleanup and repair plan

**Remove** — with a one-line reason each. Anything ambiguous is listed here
for approval, never deleted in advance.
**Replace** — sensitive fixtures and sample data → synthetic equivalents.
**Repair** — defects blocking install / start / build / test / central flow,
each with the evidence it is broken.
**Document** — README, .env.example, license, and anything else being written.
**Explicitly not doing** — scope deliberately left alone, so the boundary is
visible.

## 6. Release-method recommendation
The three options, the recommendation, and the reasoning. If a fresh-history
export would erase contributor attribution or violate an inbound license
notice requirement, say so here.

## 7. Verification performed
Commands actually run and their real results. Anything NOT RUN, with why.

## 8. Verdict
**Not ready** / **Conditionally ready** / **Ready for implementation work**
— one paragraph of justification.

Awaiting answers to §4 and approval of §5 before any changes are made.
```

## 2. Severity scale

| Severity | Meaning | Examples |
| --- | --- | --- |
| **Blocker** | Publication is not possible until resolved | Unresolved ownership; live credential; third-party material without redistribution rights; confidential client content |
| **High** | Publishing without fixing causes real harm or makes the repo useless | Personal data in history; no license on a "template"; project cannot be installed |
| **Medium** | Materially degrades the release | Central flow broken; README describes a version that no longer exists; internal hostnames in config |
| **Low** | Worth fixing, harmless if it slips | Build artifacts committed; stale badges; oversized assets |

Severity is about consequence of publication, not effort to fix.

## 4. Release-method command sequences

Hand these back in the final report. **Do not run them.** Each assumes the
audit is complete and the owner has approved the method.

### Method 1 — sanitize in place, preserve history

Only when history is clean, or after rewriting it. History rewriting changes
every subsequent SHA and breaks every existing clone, fork, and open PR.

```bash
# 1. Back up first. This is not reversible.
git clone --mirror /path/to/repo /path/to/repo-backup.git

# 2. If secrets must be purged from history (git-filter-repo, installed
#    separately). Run on a fresh clone; filter-repo refuses a dirty one.
git filter-repo --path .env --invert-paths
git filter-repo --replace-text /path/to/replacements.txt   # value → ***REMOVED***

# 3. Re-scan the rewritten history before going further.
bash scripts/scan-release-surface.sh --repo . --out /tmp/rescan

# 4. Force-push the rewritten history, then flip visibility in repo settings.
#    Coordinate first: everyone with a clone must re-clone.
git push --force --all && git push --force --tags
```

Rotation happens at the provider regardless. Rewriting history does not
invalidate a credential, and forks may retain the original objects.

### Method 2 — fresh-history snapshot into a new public repo (usual choice)

The original private repo is left completely untouched.

```bash
# 1. Export the sanitized tree with no git history attached.
#    git archive emits tracked files only — untracked and ignored files
#    cannot leak through it.
mkdir /tmp/public-snapshot
git archive --format=tar <sanitized-branch> | tar -x -C /tmp/public-snapshot

# 2. Scan the snapshot as its own artifact before it becomes a repo.
bash scripts/scan-release-surface.sh --repo /tmp/public-snapshot --out /tmp/final-scan
#    (No history yet, so --skip-history is equivalent here.)

# 3. Verify from the snapshot exactly as a stranger would.
cd /tmp/public-snapshot && npm ci && npm test && npm run build

# 4. Initialize fresh history with a single commit.
git init -b main && git add -A
git commit -m "Initial public release

<one-paragraph description of what this is and its maintenance status>"

# 5. Create the new PUBLIC repo on the host and push. Owner's action.
#    Verify the visibility setting on the creation screen before pushing.
git remote add origin <new-public-repo-url>
git push -u origin main
```

Why `git archive` rather than `cp -r`: copying a directory brings untracked
and ignored files — including the `.env` that was never committed — straight
into the snapshot. `git archive` cannot.

### Method 3 — stay private

No commands. Record the specific unresolved risk, what would have to change to
revisit, and who would need to answer. A blocked release with a clear reason is
a real outcome, and it is the right one when ownership or confidentiality
cannot be settled.
